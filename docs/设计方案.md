# 行知教研吧（xgz-bbs）设计方案 v0.1

> 校内教师教研协作平台：课题组发帖 / 评论 / 交任务 / 传附件
> 技术栈：Python + Flask + SQLite　｜　形态：单机部署，校内网访问

---

## 1. 定位与典型场景

一句话：**把"课题组"搬成一个可以发帖、回复、派活、交材料的地方。**

典型流程（以省级课题为例）：

```
组长建"课题组" → 拉老师入组
      ↓
组长发【话题】：「开题报告初稿讨论」        → 组员回复/评论
组长发【任务】：「10月10日前交文献综述」     → 指派 3 位老师
      ↓
老师看到任务 → 回复讨论 → 上传附件 → 点"标记完成"
      ↓
组长收到通知 → 查看附件 → 「确认通过」或「打回，请补充」
      ↓
结题时一键导出：该课题全部话题 + 讨论 + 任务 + 附件打包
    
核心是三条线：**讨论线（帖子/评论）**、**任务线（指派/提交/审核）**、**材料线（附件）**。

## 2. 技术选型

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **Flask + Jinja2 服务端渲染** | 无 npm、无构建，一套代码看懂就能改；单机部署极简 | 页面整页刷新，交互朴素 | ✅ 采用 |
| FastAPI + Vue/React | 交互体验好 | 需要 Node 构建链，学校没人接手维护 | ❌ |
| Streamlit | 一天出东西 | 做不了论坛/权限/附件的形态 | ❌ |
| Django | 自带 admin 后台 | 对"看得懂"这个目标太重 | 备选 |

具体：

- **后端**：Flask 3.x + 蓝图分模块
- **数据**：SQLite（单文件 `data/bbs.db`，开启 WAL，并发几十人无压力）
- **模板**：Jinja2；**前端**：手写一份 CSS + 少量原生 JS，不引任何前端框架
- **附件**：存本地 `data/uploads/年/月/`，数据库只存元数据
- **启动**：`python run.py`，或双击 `启动.bat`；生产用 `waitress`（Windows 友好，替代 Flask 自带的开发服务器）
- **数据访问**：纯 SQL（`sqlite3` 标准库），不上 ORM —— 表就十来张，SQL 比 ORM 更好读好改

> 规模判断：全校百来位老师、几十个课题组、附件若干 GB，SQLite 完全够。真到了并发瓶颈（几百人同时刷），再迁 PostgreSQL，SQL 几乎不用改。

## 3. 功能规划

### P0 —— 先跑起来（第一期就做这些）

1. **账号**：管理员建号 / Excel 名单批量导入；密码 pbkdf2 加盐哈希；角色 = 管理员 / 教师
2. **课题组**：组长建组、加成员、设组长；每组成员可见
3. **话题**：发帖（讨论 / 公告）；回帖，支持"楼中楼"（回复某层）
4. **任务**：组长发任务（标题、说明、截止日期、附件、指派给谁）；一个任务可指派多人，**每人独立状态**
5. **提交与审核**：老师"标记完成 + 交文字/附件"；组长"确认通过 / 打回"（打回可附意见）
6. **附件**：上传、下载、图片与 PDF 页内预览；限制单文件大小与扩展名黑名单
7. **通知**：被回复、被 @、被指派任务、任务被打回 → 右上角未读角标
8. **管理后台**：用户增删改、重置密码、版块管理

### P1 —— 用顺手之后加

9. **全文搜索**（SQLite FTS5，中文用分词或 bigram 兜底）
10. **我的任务**聚合页：跨课题组汇总我名下所有任务，按截止日期排序，逾期标红
11. **课题进度看板**：任务完成率、成员贡献统计（结题汇报直接用）
12. **一键导出课题材料**：整课题的话题 + 全部讨论 + 任务 + 附件打成 zip —— 结题时最值钱的功能
13. 点赞 / 已读回执 / @提醒

### P2 —— 锦上添花

14. Markdown 编辑器 + 图片粘贴直接上传
15. 移动端适配（老师用手机看通知）
16. 企业微信 / 公众号消息推送
17. 与校本资源库、NAS 打通（附件直接落 NAS）

## 4. 数据模型

SQLite，12 张表。

```
users            id, username, password_hash, display_name, subject(学科),
                 role(admin|teacher), avatar_seed, is_active, last_login_at, created_at

boards           id, name, description, kind(project|general), cover_color,
                 is_public, is_archived, owner_id, created_at
board_members    board_id, user_id, role(leader|member), joined_at      [联合主键]

topics           id, board_id, author_id,
                 kind(存的是 topic_kinds.code，管理员可增删),
                 title, body, body_format(text|html),
                 is_pinned, is_featured, status(open|closed),
                 view_count, reply_count, last_reply_at, last_reply_uid,
                 created_at, updated_at

topic_kinds      id, code(入库值), label(中文名), color(调色板键), sort_order,
                 leader_only, pinnable, is_builtin(不许删), is_active(停用), created_at

posts            id, topic_id, author_id, parent_id(楼中楼), floor_no,
                 body, body_format(text|html), is_deleted, created_at, updated_at

tasks            id, topic_id(UNIQUE 1:1), board_id, title, detail,
                 due_date, created_by, status(open|closed), created_at
task_assignees   id, task_id, user_id,
                 status(todo|doing|done|confirmed|rejected),
                 submission_post_id, submitted_at, reviewed_by, reviewed_at,
                 review_note                                          [task_id+user_id 唯一]

attachments      id, owner_id, board_id, attachable_type(topic|post|task_sub),
                 attachable_id, orig_name, stored_path, ext, mime,
                 size_bytes, sha256, download_count, created_at

notifications    id, user_id, actor_id, kind, board_id, topic_id, post_id,
                 task_id, summary, is_read, created_at

reactions        id, target_type(topic|post), target_id, user_id,
                 kind(like|ack), created_at
settings         key, value
```

### 三个关键设计选择

**① 任务 = 话题的一种类型，而不是独立模块**
`topics.kind = 'task'`，扩展信息放 `tasks`（1:1）。这样讨论和任务共用同一套"详情页 + 回复 + 附件"逻辑，代码量少一半；同时"我的任务"页可以跨课题组聚合。

**② 一个任务指派给多人，每人一条 `task_assignees` 记录**
省级课题组通常是"这件事 3 位老师分别做"，所以状态必须挂在"人 × 任务"上，而不是任务上。

**③ 附件用多态关联（`attachable_type` + `attachable_id`）**
一份上传逻辑同时服务"帖子附件""任务说明附件""任务提交附件"，不用建三张表。

### 话题类型（kind）：存在库里，管理员自助增删

类型清单存在 `topic_kinds` 表里，管理员在「管理后台 → 类型标签」里加/改/排序/停用/删除 ——
**加一个标签不用改代码、不用改 CSS、不用重新部署**。

```
topic_kinds      id, code(入库值，建后不可改), label(界面中文名), color(调色板键),
                 sort_order, leader_only(仅组长可发), pinnable(可置顶),
                 is_builtin(代码里有专门流程，不许删), is_active(停用), created_at
```

代码侧只有一个入口 `app/kinds.py`，其它位置不许再写死类型列表：

| 函数 | 用途 |
|---|---|
| `all_kinds()` | 全部类型（含停用），按显示顺序；按请求缓存 |
| `order()` / `postable()` | 标签栏顺序 / 可发布的类型（都只含启用中的） |
| `codes()` | 筛选白名单（**含停用类型**，这样旧链接、历史筛选照样能打开） |
| `leader_only()` / `pinnable()` | 发布权限、是否可置顶 |
| `free_labels()` | 组员可发的类型名，发布页提示语直接用 |
| `can_delete()` / `can_disable()` / `usage()` | 删除与停用的安全闸 |

**内置类型**（`discussion` / `notice` / `task`）由 `config.BUILTIN_KIND_CODES` 锁定：
- `task` 会建 `tasks` 行、进「我的任务」、带指派与审核；`notice` 发布时通知全组；
  `discussion` 是类型非法时的兜底值 —— 三者都**不许删**、`code` 不许改；
- `discussion` 额外**不许停用**（`UNDISABLABLE_KIND_CODES`），否则发布页没有默认类型。

其余规则：
- **有话题在用的类型不许删**（否则那些话题的标签就没了），引导改用「停用」；
  停用后发布页不再出现，历史话题照常显示、照常能搜到 —— 与账号「停用而非删除」同一思路。
- `code` 创建后不可改：`topics.kind` 存的就是它，改了历史标签就对不上。
- 颜色只存**调色板键**（`config.PALETTE`，如 brand/ok/purple），CSS 里对应 `.t-c-<键>`。
  所以后台换颜色即时生效，也不用动 CSS。标签类名由 `_macros.kind_tag` 查表生成，
  未知类型兜底 `.t-c-soft`。

`config.py` 里留的 `DEFAULT_TOPIC_KINDS` / `TOPIC_KIND` 等只在两处生效：
① 首次建库灌种子（`kinds.seed_defaults`，已存在的 code 一律不动）；
② 表读不到时兜底，保证页面照样渲染。

所有类型共用同一套附件上传（`upload_area` / `claim_attachments` 与 kind 无关），
所以新建的类型天然支持传附件，不需要额外接。

### 正文富文本（body_format）：老帖一行不动

正文有两种存法，用 `topics.body_format` / `posts.body_format` **逐行**标记：

| 值 | 谁产生 | 渲染方式 |
|---|---|---|
| `text` | 升级前的全部老数据；浏览器没开 JS 时的降级提交 | 转义输出 + CSS `white-space:pre-wrap` 保留换行（**与升级前完全一致**） |
| `html` | 编辑器 JS 提交（表单里 `body_format` 被设成 `html`） | 白名单清洗后按 HTML 渲染 |

**为什么不像对话类型那样只加一张表？** 因为正文是行内数据，没有"逐行不动老数据"之外的
更安全做法：不改老行、只加一个默认值为 `text` 的新列，升级后老帖的渲染路径一个字节都没变。

**加字段怎么落到老库上**：`CREATE TABLE IF NOT EXISTS` 只管建新库，SQLite 又没有
`ADD COLUMN IF NOT EXISTS`。所以 `app/db.py` 里有一张 `_ADDED_COLUMNS` 清单，
`init_db()` 启动时用 `PRAGMA table_info` 查一遍，缺什么补什么（**只加列、不动老数据，可重复运行**）。
以后再加字段，往那张清单里追加一行即可。

**安全模型（`app/richtext.py`）：把数据库当成不可信来源，洗两遍。**

| 环节 | 函数 | 行为 |
|---|---|---|
| 入库 | `parse_body(form, max_chars)` | 走 `sanitize_html` 白名单清洗；编辑器空白时存 `''` 并把格式复位成 `text` |
| 出库 | `rich_body(text, fmt)` | 渲染时**再洗一遍**，模板里当 `Markup` 用；改完 render 也安全 |
| 导出/摘要 | `to_plain(text, fmt)` | 脱标签转纯文本（材料 zip、搜索摘要、`@提及` 匹配都用它） |

白名单与处置策略：

- **放行**：`p br div span strong b em i u s del ins mark ul ol li blockquote code pre hr a h2 h3 h4`
- **脱标签留内容**（`<div>` → 内容保留）：白名单之外的普通标签
- **连内容一起丢**：`script style iframe object embed svg math textarea form input video audio canvas …`
  —— 免得把代码当正文显示出来，看起来像故障
- **属性**：只留 `<a>` 的 `href` / `title`，其余（含 `style`、`on*`）全丢；
  `href` 只认 `http/https/mailto/tel` 与相对路径，且**先抹掉所有控制字符再判断**
  （`java\tscript:` 这类就是靠制表符/换行绕过的）；`<a>` 自动补 `rel="noopener noreferrer" target="_blank"`
- 嵌套深度上限 24 层；单篇正文长度上限 `config.BODY_MAX_CHARS`（默认 20000），
  超长**明确报错**而不是静默截断

**编辑器（不引任何前端依赖）**

`_macros.rich_editor()` 一个宏，发布 / 编辑 / 回复 / 任务提交四处共用。
用的是 `contenteditable` + `document.execCommand`（虽被标记 deprecated，但主流浏览器至今完整支持；
自己手撸 Range 反而更容易踩兼容坑）。工具栏：加粗、斜体、下划线、删除线、项目符号、编号、
引用、代码、链接、清格式、表情。

**降级路径是刻意设计的**：宏默认渲染成普通 `<textarea>`（可编辑区与工具栏都带 `.hide`）——

- **没开 JS**：用户看到的就是原来那个 textarea，提交纯文本，`body_format` 保持 `text`，
  走的还是升级前那条路；
- **开了 JS**：`app.js` 把工具栏与可编辑区亮出来、藏起 textarea，每次输入把
  `innerHTML` 同步回 textarea，并把 `body_format` 设成 `html`。

textarea 里放的**始终是纯文本**（HTML 内容先经 `to_plain` 转一遍）。这样即使 JS 半路出错，
老师打开编辑页看到的也是可读文字而不是空框，不会一保存就把正文清空。

**粘贴**：一律 `preventDefault` 后取 `text/plain` 插入。从 Word / 网页复制的内容带着大量
内联样式和隐藏标签，服务端反正会剥掉，与其粘完变形不如直接给干净文字。

**表情**：`config.EMOJI` 里一组精选表情（72 个，教研场景常用的那批），
面板点一下就用 `execCommand('insertText')` 插到**光标处**（插入前先恢复保存的选区，
所以点面板不会丢失插入位置）。存的是**字符本身**而不是图片，因此搜索、导出、复制粘贴都正常。

## 5. 权限模型

角色分两层：**系统角色**（admin / teacher） × **组内角色**（leader / member）。

| 操作 | 管理员 | 组长（本组） | 组员 | 非成员 |
|---|---|---|---|---|
| 浏览课题组 | ✅ | ✅ | ✅ | 仅"公开组"，否则 403 |
| 发讨论帖 / 回帖 | ✅ | ✅ | ✅ | ❌ |
| 发任务 / 公告 | ✅ | ✅ | ❌ | ❌ |
| 置顶 / 加精 / 关闭话题 | ✅ | ✅ | ❌ | ❌ |
| 编辑、删除自己的帖子 | ✅ | ✅ | ✅（限 30 分钟内） | ❌ |
| 删除他人帖子 | ✅ | ✅ | ❌ | ❌ |
| 提交任务 | — | ✅ | ✅ | ❌ |
| 确认 / 打回 | ✅ | ✅（本组） | ❌ | ❌ |
| 下载附件 | ✅ | ✅ | ✅ | 按所属组可见性判断 |
| 用户管理 / 建组 | ✅ | 仅管本组成员 | ❌ | ❌ |
| 标签增删改 / 发布权限 | ✅ | ❌ | ❌ | ❌ |

> 其它类型（方案 / 记录 / 作品 / 资源 / 培训 / 成果 / 后台自建的）默认**全员可发**；
> 管理员给某个标签勾上「仅组长可发布」后就与任务、公告同权，判定逻辑走
> `kinds.leader_only()`，不写死类型名。

权限收口在两个装饰器里：`@login_required` 和 `@board_role_required('leader')`，避免每个视图里散落 if 判断。

## 8. 关键实现细节

**附件安全**
- 落盘文件名用 `uuid4().hex + 原扩展名`，**绝不使用原名**（防路径穿越、防中文乱码）
- 扩展名走白名单（doc/docx/pdf/xls/xlsx/ppt/pptx/jpg/png/zip/mp4…），黑名单可执行文件
- 单文件上限默认 50MB（可在 `config.py` 调）；校验 `content-length` 与真实写入字节数
- 下载路由先查 `attachments` → 反查所属课题组 → 校验当前用户可见性 → 再 `send_file(as_attachment=True)`

**任务状态机**

```
        ┌──────── 打回，附意见 ────────┐
        ↓                              │
     [todo 待办] ──→ [doing 进行中] ──→ [done 已提交] ──→ [confirmed 已通过]
                         ↑    
   组长指派即产生 todo；老师点"开始做"→doing；提交后→done；组长审核→通过/打回
```

**时间处理**：数据库统一存 UTC 整数时间戳，展示时统一转 `Asia/Shanghai`，避免服务器时区问题。
**备份**：每次启动 + 每日 02:00 复制 `bbs.db` 到 `backups/bbs-YYYYMMDD.db`（SQLite 用 `VACUUM INTO` 更安全）；附件目录另做增量拷贝。
**导出**：结题时 `GET /b/<id>/export` 生成 `课题名-20260911.zip`，内含按话题分文件夹的正文（HTML）+ 全部附件。

## 9. 部署与使用

```bash
# 首次
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
python run.py

# 老师访问
http://<这台电脑的校内IP>:8000
```

`启动.bat` 内容大致三行：激活虚拟环境 → 打印本机 IP → 启动 waitress。老师机开机自启可以丢进「任务计划程序」。
建议把 `data/` 目录放到学校 NAS 同步区（如 `\\192.168.10.201\xykp` 下的子目录），这样数据库和附件天然有异地副本。

## 10. 需要你拍板的事

1. **要不要开放注册**？我倾向"管理员建号 / Excel 导入"，校内平台匿名注册没意义，还容易被无关人员注册。
2. **课题组是否对外可见**？默认：本组可见，可设"公开组"让全校围观。
3. **任务是否要打分/权重**？如果结题要算贡献度，P0 就把"分值"字段预留上。
4. **附件存哪儿**？本机 `data/uploads/`，还是直接落 NAS？
5. **要不要"审核制"**（新帖需组长通过才可见）？我建议先不做，太伤流畅度。
6. **是否需要多人同时用同一台机器部署**（谁是服务器）？—— 建议用一台常年开机的办公电脑或教室机器。
